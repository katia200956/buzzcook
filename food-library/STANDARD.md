# Buzzcook 3D Food Library — технічний стандарт v2

Статус: чернетка на погодження Катюшею (2026-10-07). Жодного ассета не створюється, доки
Катюша не надіслала всі референси і не погодила цей стандарт.

## 1. Принцип

Бібліотека будується один раз і використовується всіма рецептами. Рецепт ніколи не генерує
модель. Рядок рецепта «Помідор — 100 г, кубиками» перетворюється так:

```
інгредієнт → product id (tomato)
спосіб нарізки → state id (cubes)
100 г → кількість шматків = 100 / piece_mass_g(cubes)
→ вибір шматків із GLB → розміщення в сцені → анімація дії (chop, pour, stir…)
```

Кожен продукт має **одне джерело правди**: одну збірку цілого продукту з повною внутрішньою
анатомією. Усі стани (половина, скибки, кубики…) вирізаються з цієї збірки, тому скибка
завжди візуально той самий помідор, що й цілий.

## 2. Робочий процес (для кожного продукту)

| Крок | Що робиться | Результат |
|---|---|---|
| 1. Прийом референсів | Катюша надсилає фото, вони копіюються в `products/references/<id>/` | оригінали фото |
| 2. Аналіз | Лист аналізу за чекліст §11: форма, пропорції, асиметрія, шкірка, колір зовні/всередині, анатомія, насіння, вологість, товщина нарізки на фото | `products/<id>/reference.md` |
| 3. Розміри | Реальні розміри середнього екземпляра (ботанічні дані + пропорції з фото) | поле `dimensions` у `meta.json` |
| 4. Збірка цілого | Процедурний Blender-скрипт (bpy) будує зовнішню оболонку і всі внутрішні об'єми як окремі замкнені меші | `tools/<id>.py`, `whole` |
| 5. Стани | Той самий скрипт ріже збірку булевими розрізами по частинах анатомії | GLB для кожного стану |
| 6. Матеріали | PBR за §7, спільні імена частин | `materials/` |
| 7. Перевірка | Статичні рендери (без відео) поруч із референсом, той самий ракурс і світло | `previews/*.jpg` |
| 8. Валідація | Скрипт перевіряє масштаб, імена, півоти, розмір файлу, замкненість мешів | звіт валідації |
| 9. Погодження | Катюша дивиться прев'ю; лише після «так» продукт іде в каталог | запис у каталозі |

Порядок: спочатку один продукт проходить усі 9 кроків як еталон (пропоную помідор), потім
решта продуктів пакетами за тим самим скриптом-шаблоном.

## 3. Масштаб і система координат

- **Одиниці:** метри, реальний розмір. Середній помідор ≈ 0.070 м у діаметрі.
- **Формат:** glTF 2.0 binary (`.glb`). Осі glTF: **+Y вгору, +Z вперед (до камери), +X вправо**.
  У Blender (Z вгору) моделюємо як звично, експортер конвертує осі.
- **Орієнтація продукту:**
  - круглі плоди (помідор, цибуля, лимон, яблуко): вісь росту (плодоніжка → верхівка) по +Y,
    плодоніжка вгорі, так як продукт лежить на дошці;
  - видовжені (банан, огірок, морква, кабачок): довга вісь по X, лежить на боці у природній
    стійкій позі, вигин банана опуклістю до −Y;
  - плоскі (хліб, сир, м'ясо): найбільша площина паралельна XZ.
- **Поверхня:** усе стоїть на площині Y = 0, нічого не провалюється нижче.

## 4. Півоти (origin)

| Об'єкт | Де півот | Навіщо |
|---|---|---|
| Корінь файлу (`<id>_<state>`) | центр низу всієї групи, Y = 0 | поставити на дошку/тарілку однією координатою |
| Цілий продукт | центр низу (точка опори) | ставиться і котиться природно |
| Кожен шматок (скибка, кубик, чверть) | центр мас шматка | обертання, падіння, підкидання в анімаціях |
| Масa (mashed) | центр низу | заповнює ємність знизу |

**Розміщення шматків у файлі:** кожен шматок лежить **на своєму місці всередині цілого продукту**
(«зібрана поза»). Тоді анімація нарізки = цілий продукт → ті самі шматки, які лише розсуваються.
Розкладку на дошці, «парящі шари» як на фото, купку в мисці робить застосунок, а не файл.

## 5. Іменування

- **product id:** англійською, kebab-case, однина: `tomato`, `onion-red`, `bell-pepper-yellow`.
  Український рядок рецепта шукає продукт через `names.uk` і `aliases` у `meta.json`.
- **state id:** закритий список із §8 (`whole`, `half`, `quarter`, `slices`, …).
- **Файли:** `<id>_<state>[_<variant>].glb`, наприклад `tomato_slices_thin.glb`,
  `tomato_cubes.glb`, `tomato_cooked_stewed.glb`.
- **Вузли в GLB:** `<id>_<state>` (корінь) → `<piece>_<NN>` (шматки, двозначний номер,
  тризначний від 100 шматків): `slice_00 … slice_07`, `half_00`, `quarter_00 … quarter_03`,
  `cube_00 …`. Один шматок = один меш, частини анатомії в ньому — окремі матеріали
  (примітиви), тож шматок рухається як одне ціле.
- **Матеріали:** ім'я частини зі спільного словника §7 (`skin`, `flesh`, `gel`, `seed`, …).
  Колір конкретного продукту задається параметрами матеріалу, ім'я не змінюється.
- **Текстури:** `<id>_<part>_<map>.<ext>`: `tomato_skin_basecolor.jpg`, `tomato_skin_normal.png`,
  `tomato_skin_orm.jpg`.

## 6. Геометрія і рівень деталізації

- **Внутрішня анатомія — справжня 3D-геометрія.** Стінки, камери, гель, насіння, серцевина,
  шари, кісточки моделюються об'ємами і ріжуться разом із продуктом. Фото чи текстура на
  пласкому зрізі заборонені.
- **Меші замкнені (watertight)**, без самоперетинів, нормалі назовні. Це потрібно для булевих
  розрізів, фізики й заповнення ємностей.
- **Природна асиметрія:** без ідеальної симетрії. Шум форми, нерівні ребра, різна кількість
  камер, різний розмір насінин. Кожен продукт має фіксований `seed`, тож перезбірка дає
  той самий продукт.
- **Варіація шматків:** товщина скибок ±8 %, розмір кубиків ±10 %, кут зрізу ±3°, бо ніж
  ріже нерівно. Жоден шматок не є копією іншого.
- **Колайдер:** кожен шматок має спрощений опуклий меш `<piece>_<NN>_col` (до 64 трикутників),
  прихований, для фізики падіння і змішування.

Бюджети (трикутники, для телефона):

| Що | LOD0 (крупний план) | LOD1 (сцена) |
|---|---|---|
| Цілий продукт | ≤ 40 000 | ≤ 8 000 |
| Половина / чверть, кожна | ≤ 25 000 | ≤ 5 000 |
| Одна скибка | ≤ 6 000 | ≤ 1 500 |
| Один кубик / шматочок | ≤ 600 | ≤ 150 |
| Маса (mashed) | ≤ 20 000 | ≤ 5 000 |
| Файл GLB | ≤ 2.5 MB (стани з 40+ шматками ≤ 3 MB) | ≤ 0.8 MB |

LOD1 лежить в окремому файлі `<id>_<state>_lod1.glb`. Стиснення Draco і Meshopt не
використовуються (Hermes не виконує їхні WebAssembly-декодери), квантування позицій теж ні.
Колір вершин (COLOR_0) зберігається як RGBA8 (`tools/pack_colors.py`), це стандартний glTF.

## 7. Матеріали і текстури

PBR metallic-roughness, `metallic = 0` для всієї їжі. Спільний словник частин:

| Частина | Де | Шорсткість | Особливості |
|---|---|---|---|
| `skin` | шкірка помідора, яблука, перцю | 0.25–0.45 | природний блиск, мікронерівності в normal map, без «пластику» |
| `peel` | шкірка банана, цитрусових | 0.45–0.7 | пори цедри, плями |
| `rind` | кавун, сир | 0.6–0.9 | |
| `pith` | біла шкірка цитрусових | 0.8 | матова, волокниста |
| `flesh` | м'якоть | 0.35–0.6 | легке просвічування (sheen + світліший колір у товщі) |
| `gel` | гель навколо насіння | 0.05–0.15 | напівпрозорий, вологий, clearcoat |
| `seed` | насіння | 0.3–0.5 | |
| `core` | серцевина, колумела | 0.5 | |
| `layer` | шари цибулі | 0.3 | тонкі краї іншого кольору |
| `vesicle` | соковиті мішечки цитрусових | 0.1 | вологі, clearcoat |
| `calyx` / `stem` | чашолистки, плодоніжка | 0.6–0.8 | матові, сухуваті краї |
| `crust` / `crumb` | хліб | 0.8–0.95 | |
| `meat` / `fat` | м'ясо, сало | 0.4–0.6 | волокна в normal map |
| `yolk` / `white` | яйце | 0.2–0.4 | |
| `puree` | маса | 0.15–0.3 | вологе, clearcoat |

- **Вологість:** свіжий зріз завжди вологий: `KHR_materials_clearcoat` (0.4–0.8) на гранях зрізу.
  Грані зрізу мають окремий матеріал-слот `<part>_cut`, щоб застосунок міг «підсушувати» їх
  або додавати сік під час анімації.
- **Колір:** основний колір кожної частини лежить у кольорі вершин (COLOR_0), матеріал дає
  шорсткість, блиск і вологість. Так шкірка має плямки й жовтуватість біля плодоніжки без
  текстур.
- **Колір усередині товщі:** через vertex color (темніше біля шкірки, світліше в центрі), не
  через фото.
- **Текстури:** лише там, де потрібна фото-поверхня (пори цедри, шкірка цибулі, скоринка).
  Base color — sRGB JPEG; normal — PNG; ORM (occlusion/roughness/metal) — JPEG. Максимум
  1024 px, 2048 px лише для шкірки цілого продукту в LOD0.
- **Стан «cooked»** — окремі значення матеріалу (темніший, менш блискучий, м'якші краї) плюс
  легка деформація (усадка 5–20 %), не нова модель з нуля.
- **Перевірочне світло** однакове для всіх продуктів: м'яке розсіяне з лівого верхнього кута,
  теплий біло-бежевий фон, як на референсах Катюші.

## 8. Стани і правила нарізки

| state id | Що | Стандартні розміри |
|---|---|---|
| `whole` | цілий продукт | реальний розмір |
| `half` | рівно навпіл | розріз через вісь росту (`half`) або поперек (`half_cross`) |
| `quarter` | чверті | 4 частки вздовж осі |
| `wedges` | часточки | 6–8 часток вздовж осі (лимон, картопля, яблуко) |
| `slices` | скибки / кружальця | `thin` 3 мм, `medium` 6 мм, `thick` 10 мм |
| `half_slices` | півкружальця | 6 мм |
| `rings` | кільця (цибуля, перець) | 5 мм |
| `strips` | соломка / смужки | 8 × 8 мм × довжина продукту; `julienne` 3 × 3 × 50 мм |
| `cubes` | кубики | 15 мм |
| `diced` | дрібні нерівні шматочки | 6–8 мм |
| `chopped` | дрібно посічене | 2–4 мм |
| `mashed` | пюре / роздавлене | `crushed` (шматочки в соку), `puree` (гладке) |
| `peeled` | очищений цілий | без шкірки, з відповідною поверхнею під нею |
| `cooked` | приготований | варіанти: `fried`, `stewed`, `roasted`, `boiled`, `grilled` |
| `parts` | окремі частини | `skin`, `seeds`, `flesh`, `juice`, `zest`, `core` … |

Стан, що не має сенсу для продукту, не створюється (пюре з цибулі-ріпки, очищений лимон
кубиками тощо). Для кожного продукту список станів фіксується в `meta.json` до початку
моделювання і погоджується разом з аналізом референсів.

**Маса стану** (`piece_mass_g`) рахується з об'єму шматка в Blender × густина продукту, а не
вгадується. Застосунок ділить грами з рецепта на масу шматка і бере стільки шматків
(з округленням і випадковим вибором з усіх варіантів).

## 9. Структура продукту

```
food-library/products/<id>/
  meta.json            метадані (схема: food-library/schema/meta.schema.json)
  reference.md         аналіз референсів (§11)
  tools/<id>.py        Blender-скрипт: збирає цілий продукт і ріже всі стани
  whole/               <id>_whole.glb, <id>_whole_lod1.glb, preview.jpg
  half/
  quarter/
  slices/              <id>_slices_thin.glb, …_medium.glb, …_thick.glb
  strips/
  cubes/
  diced/
  chopped/
  mashed/
  peeled/
  cooked/
  <інші стани продукту>/
  materials/           materials.json — значення PBR для кожної частини
  textures/            <id>_<part>_<map>.jpg|png
  previews/            порівняння з референсом
```

У репозиторії лежать `meta.json`, `reference.md`, скрипт, `materials.json` і прев'ю.
GLB і текстури лежать на CDN Higgsfield за тим самим шляхом (`<id>/<state>/<file>`);
у `meta.json` записані їхні URL. Поки продукт не погоджено, GLB лежать у файлах проєкту
(`products/v2/<id>/`), на CDN вони йдуть разом із підключенням до застосунку.

Команди:
```
python products/<id>/tools/<id>.py --out <build> --preview <dir>   # bpy 5.2
python tools/validate.py products/<id> <build>                     # перевірка за стандартом
python tools/update_meta.py products/<id> <build>                  # маси й файли в meta.json
``` Так репозиторій лишається легким, а структура однакова.

## 10. Метадані

Схема: [`schema/meta.schema.json`](schema/meta.schema.json). Обов'язкові поля:

- `id`, `names` (`uk`, `en`), `aliases` — для пошуку з тексту рецепта;
- `category` (`vegetable`, `fruit`, `herb`, `grain`, `dairy`, `meat`, `fish`, `bakery`, …);
- `dimensions_m` — середні реальні розміри і діапазон;
- `mass_g` (середня і діапазон), `density_g_cm3`;
- `edible_parts`, `inedible_parts`, `waste_ratio` (частка відходів після чистки);
- `states` — для кожного стану: файли, `piece_mass_g`, кількість шматків, розміри шматка, статус
  (`planned` / `built` / `approved`);
- `preparation` — типові способи підготовки;
- `cooking_actions` — рекомендовані дії анімації (`slice`, `dice`, `crush`, `stir`, `pour`,
  `place_in`, `fry`, `simmer` …) і стан, у якому продукт для неї потрібен;
- `look` — короткий підсумок аналізу референсу;
- `build` — `seed`, версія скрипта, дата збірки.

## 11. Чекліст аналізу референсу

Для кожного фото записується в `reference.md`:

1. Загальна форма, пропорції (висота : ширина), асиметрія, сплющення, ребристість.
2. Шкірка: колір (кілька HEX-проб), градієнт, плями, пори, блиск, тріщинки, краплі вологи.
3. Плодоніжка, чашолистки, кінчики: форма, колір, сухість.
4. Зріз: товщина шкірки/стінки, кількість і форма камер, перегородки, серцевина, шари, вени.
5. Насіння: кількість, розмір, колір, як розташоване, у чому сидить (гель, м'якоть).
6. М'якоть: колір від краю до центру, прозорість, волокна, вологість, сік на зрізі.
7. Товщина скибок на фото, рівність зрізу.
8. Світло і фон фото (щоб перевірочний рендер можна було поставити поруч).
9. Що на фото **неприродне** (надто ідеальна симетрія, AI-артефакти) і не повинно потрапити
   в модель.
10. Список станів, які має сенс зробити для цього продукту.

## 12. Готовність ассета (Definition of Done)

- Масштаб у метрах збігається з `dimensions_m` (±5 %).
- Імена файлів, вузлів, матеріалів за §5; півоти за §4.
- Усі шматки стану разом складаються в цілий продукт без зазорів.
- Меші замкнені, є колайдери.
- Файл у межах бюджету §6.
- Прев'ю поруч із референсом: однаковий колір, пропорції, анатомія.
- `piece_mass_g` пораховано з об'єму.
- Катюша погодила прев'ю.

## 13. Інструменти

- Blender 4.2 (`bpy`) — процедурна збірка, один скрипт на продукт, детермінований через `seed`.
- Збірка і завантаження на CDN — у пісочниці Higgsfield (контейнер не має доступу до CDN).
- Перевірка — статичні рендери Blender (Eevee/Cycles), без відео.
- У застосунку — three.js через `@react-three/fiber` + `expo-gl` (додається, коли буде
  перший погоджений продукт).
